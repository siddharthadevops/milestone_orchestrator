# Creativity: Evolutionary Search for Useful Possibilities

Mandate: the frozen launch snapshot in
`implementation/milestones/creativity/goal.md`. This document is the milestone's
planning contract; each slice note will define its bounded implementation and
verification surface when that slice starts.

## Register 1 — Intent (lay language)

### What this builds

This milestone adds an independently orderable creativity task for an operator
who has an objective but cannot see a useful way forward. The operator supplies
the objective, facts, constraints, context, and optional reference material. A
first model call turns that problem into a compact set of meaningful parts that
code can combine. Code then explores combinations, while evaluation calls
explain and score the resulting proposals against the operator's objective.

The task is not a title generator, a business planner, or a collection of
domain recipes. The same fixed search motor handles literary, commercial, and
other material. Material-specific prompt text may improve what the models look
for, but it cannot replace the operator's objective or create another engine.

The result is a short list for a human to assess. Each proposal carries its
components, explanation, assumptions, and score, together with an honest reason
the search ended. Scores rank an evaluation against this task's criteria; they
are not probabilities or promises that a proposal will work. Finding no valid
proposal is a successful, explicit exploration outcome rather than a fabricated
answer.

### How exploration behaves

Facts and hard constraints stay outside the changing material. Candidates vary
only the problem-dependent dimensions created for this task. The driver keeps
strong valid candidates, reserves room for structurally different ones, crosses
their components, and applies ordinary mutation during productive generations.
Invalid candidates never become parents, survivors, or final proposals.

Progress is measured from the best valid score at the start of an observation
window. Several small gains can therefore add up to progress; a worse average
or one disappointing generation cannot by itself declare stagnation. Once a
full patience window passes without the configured gain, a dedicated model call
may add variants to the existing dimensions. The best candidates survive that
expansion and a new observation window begins. The first version does not change
the dimension schema.

Candidate evaluation is grouped into bounded batches, and a bounded number of
batches may run at once. One evaluator is a complete configuration. Each
physical call reads the live material, prompt, and staffing authorities before
dispatch. A selection comparison uses scores from one actual
`(material, agent, model, effort)` regime; if that regime changes within or
between waves, prior-regime scores cannot enter the next selection. The current
valid survivors are scored again without old scores or prestige; the new best
becomes the reference, and that rebaseline cannot count as creative progress.

### Ownership and boundaries

The creativity driver owns the population, generations, selection, crossover,
mutation, progress window, expansion decisions, work limits, and stop reason.
Models own only the semantic jobs: constructing search material, interpreting
and evaluating candidates, and suggesting new variants after stagnation.

The existing task service owns admission, task identity, workspace exclusion,
pause, explicit resume, cancellation, terminal envelopes, access, and deletion.
Prompt Router remains the only prompt authority. Staffing Router remains the
only family, model, and effort authority. Existing runner evidence and task
accounting remain the only physical-call and cost authority. The panel remains
a projection of those records.

This milestone does not act on proposals; edit a manuscript; launch a business
initiative; classify domains automatically; create a model ensemble; change a
problem's dimensions after launch; or offer score-target completion. It adds no
new scheduler, queue, provider, permission system, model router, prompt version,
snapshot, cache, retry policy, recovery service, accounting ledger, or durable
child task per candidate or evaluation batch. It adds no third-party runtime
dependency and changes no granted additional root.

### Guarantee posture

- **Strict:** admitted configuration and model replies satisfy closed structural
  contracts; the compact objective, facts, constraints, and criteria carried to
  later calls do not evolve with candidates; every genome names one known
  variant per dimension; evaluator-reported invalid candidates are excluded;
  all configured population, generation, evaluation, concurrency, mutation,
  patience, expansion, and shortlist bounds are enforced; progress uses the
  cumulative best-valid comparison; each selection/progress comparison uses one
  actual evaluator regime, and a regime change re-evaluates the bounded
  comparison set without progress credit; normal completion reports its actual
  stop reason; and every recorded physical call contributes once to aggregate
  accounting.
- **Optimistic:** staffing documents, staffing sessions, material, and prompt
  files keep their existing live-reading semantics. Each authority is read
  afresh for every physical call; a completed save governs the next call not
  already dispatched, with no transaction across those authorities and no
  rewrite of a dispatched call. Prompt text has no version or change event and
  does not create a rebaseline obligation.
- **Eventual:** the panel may lag the latest durable search checkpoint by its
  ordinary polling interval. Display freshness never chooses work or completion.
- **Best-effort:** semantic faithfulness, real-world feasibility, score
  calibration, creative quality, and meaningful rather than merely structural
  difference remain model judgments for the operator to assess. Structural
  validation and diversity do not pretend to prove those semantic qualities.

Exploration-only means all three semantic jobs are instructed to read material
and return proposals or search data without editing files or acting on proposals;
the driver schedules no proposal execution. Worker compliance, including the
additional-root read-only rule, uses the existing full-access trust posture
(`orchestrator/README.md:631-634`; `implementation/milestones/tasks-2/skeleton.md:185-204`).
JSON validation does not contain worker tool effects, and task controls promise
quiescence rather than restoration of effects from a disobedient worker.

There is no exactly-once provider-call or automatic-recovery promise. A pause or
interrupted host preserves completed checkpoints and becomes eligible for a
later explicit Resume only after existing process-quiescence checks; partial
usage or cost remains visibly partial. The existing in-call response-correction
allowance is reused, not enlarged into task retry.
